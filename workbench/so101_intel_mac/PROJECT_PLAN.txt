Feature F1: Operator-controlled recording during teleoperation
------------------------------------------------------------
Priority: P0 / first development feature.
Status: Planned.

User story:
As an operator, I want to position and move the robot continuously, then mark
recording boundaries with a key, so I can collect demonstrations without timed
record/reset phases or restarting teleoperation between episodes.

Workflow:
1. Start the session in READY: teleoperation and both previews are active;
   no demonstration frames are added to an episode.
2. START begins an episode and changes state to RECORDING.
3. FINISH closes that episode's frame buffer and schedules it for saving.
4. Return to READY while teleoperation and previews continue.
5. DISCARD drops an active episode without incrementing the saved count.
6. EXIT ends the session after resolving any active episode and pending saves.

Control state and save-job status should be separate: a save must not force a
pause in motor control. The initial version may reject START while a previous
save is pending, with a clear busy indicator; it must keep teleoperation live.

Proposed keyboard mapping (confirm during implementation):
- Space: START in READY; FINISH in RECORDING.
- Backspace: DISCARD the active episode.
- Escape: EXIT request.
- Ctrl+C: interrupt and perform best-effort cleanup.

Implementation approach:
- Extend the recording workflow rather than add a second dataset writer to
  lerobot_teleoperate.py. Expose it through the existing local launcher.
- Keep the existing timed recording mode available and unchanged by default.
- Introduce an explicit operator-controlled mode with a small state machine.
- Route input events through a thread-safe queue and consume them at control
  loop boundaries; input callbacks must not write datasets or drive motors.
- Keep a long-lived teleoperation loop; gate dataset.add_frame() by state.
- Snapshot episode data before handing it to a save worker. Define exclusive
  dataset/writer ownership; do not concurrently mutate the same episode buffer.
- Bound outstanding save work and report saving/error status. Do not silently
  drop recording frames or report success before data is committed.
- Detect key press edges and suppress repeats to avoid double transitions.
- Display state, episode identifier, duration, saved count and pending save status.
- Announce accepted state transitions using existing log_say/play_sounds.
  Speech stays outside the per-frame path and is optional/non-blocking.

Boundary and exit semantics:
- START includes frames from the next accepted capture boundary; FINISH closes
  the buffer before the next captured frame. Document this convention.
- Assign monotonically ordered frame indices and episode-relative timestamps.
- Reject an empty episode explicitly; invalid/duplicate events are harmless.
- If EXIT is requested during recording, ask the operator to finish-and-save
  or discard; maintain teleoperation until that choice is resolved.
- Flush accepted save jobs on orderly exit. On write failure, expose the error
  and preserve recoverable data; do not claim an episode was saved.
- Keep existing disconnect/torque behavior and document it in operator guidance.

Acceptance criteria:
- Collect three episodes in one session without reconnecting either arm.
- Robot tracking and previews continue between episodes and during saving.
- Only frames inside accepted START/FINISH boundaries enter saved episodes.
- DISCARD leaves the saved episode count unchanged.
- State transitions are visible; speech can be disabled with play_sounds=false.
- Held keys, duplicate commands, empty episodes and save failures are handled.
- Saved data loads through LeRobotDataset with both camera streams and actions.
- Measure control-loop timing during saving against the current 30 Hz baseline;
  agree on a regression threshold before implementation is considered complete.

Feature F2: Microphone input for the same recording controls
----------------------------------------------------------
Priority: P1 / after keyboard workflow is stable.
Status: Planned; speech engine is not selected.

- Add an optional microphone adapter that emits the same START, FINISH,
  DISCARD and EXIT events as the keyboard adapter.
- Proposed phrases: "start recording", "finish episode", "discard episode".
- Run recognition outside the control loop. Keep keyboard control available.
- Evaluate recognition latency, reliability and CPU cost on this Intel Mac.
- Prefer a local recognition option; cloud processing requires a separate
  decision about credentials, connectivity and microphone audio handling.
- Provide explicit acknowledgments and reject ambiguous commands. Prevent
  spoken system prompts from triggering recognition, e.g. push-to-talk.
- Include microphone permission/setup guidance and an unavailable-mic fallback.

Acceptance criteria:
- Spoken and keyboard events produce identical state transitions in tests.
- Recognition delays or failures do not interrupt motor control or recording.
- Prompts do not trigger unintended commands; keyboard remains functional.

Feature F4: Estimated catch-up time and spoken lag warning
--------------------------------------------------------
Priority: P1 / following the keyboard recording foundation.
Status: Planned; estimator and thresholds require validation on this SO101.

User story:
As an operator, I want a spoken warning when the follower is estimated to need
one second or more to reach the leader's current pose, so I can slow down or
pause my movement without watching joint telemetry continuously.

Definition and assumptions:
- Estimate time to reach the CURRENT leader pose, assuming the leader stops
  moving now. This is not a prediction of the leader's future motion or a
  measurement of a one-second delay between motion histories.
- Reaching a pose means all monitored joints are within configured position
  tolerances, rather than mathematically exact equality.
- Estimate time for each joint; use the maximum as the arm-level estimate,
  initially assuming joints can move simultaneously. Validate that assumption
  under coupled motion, load and the actual motor/controller settings.
- A starting approximation is remaining error outside tolerance divided by
  expected closing speed. Account for acceleration/deceleration as the model
  is refined; instantaneous measured speed alone is not a reliable estimator.
- Use calibrated joint coordinates, configured joint limits and consistent
  units. Angular joints and the normalized gripper need separate profiles.
- Use the original leader-requested target and measured follower state for
  mismatch monitoring, even when max_relative_target clips motor commands.
  Include any configured clipping in the predicted convergence model.

Estimator and feedback:
- Establish initial joint-speed profiles from controlled measurements with
  representative loads. Refine with filtered velocity toward the target.
- Distinguish an empirical expected-time prediction from a theoretical lower
  bound based on maximum speed. Do not label the lower bound as expected time.
- Report confidence/availability; do not show a precise numeric ETA when the
  motion model, calibration or state measurements cannot support one.
- Handle stopped, blocked, moving-away and stale-feedback cases explicitly.
  Persistent error without progress produces a separate "not converging"
  condition rather than division by zero or a misleading finite ETA.
- Trigger an advisory at estimated catch-up time >=1.0 seconds, configurable.
  Require a short configurable persistence interval across consecutive samples
  to reject noise; that debounce is separate from the one-second ETA threshold.
- Proposed announcement: "Follower lagging, slow down." For sustained lack of
  progress, use a distinct message such as "Follower not catching up."
- Display estimated time, confidence/status, limiting joint and current error.
- Add hysteresis for warning clearance and an announcement cooldown (initial
  proposal: five seconds). Avoid queued or overlapping speech messages.
- Run speech asynchronously through the shared audio mechanism, respecting
  play_sounds=false and preventing prompts from triggering F2 voice commands.
- Share monitoring between teleop and record modes, including READY/RECORDING.
  Read available loop observations rather than adding avoidable serial polls.
- Initial behavior is advisory only: it does not automatically stop motors,
  alter targets, or pause/discard an episode. Show/log warning events and their
  timestamps for later dataset-quality review.

Acceptance criteria:
- Synthetic trajectories cover known speeds, acceleration, multiple joints,
  noise, clipping, zero speed, moving away and stale measurements.
- Test tolerance handling, warning threshold, persistence, hysteresis, cooldown,
  unavailable estimates and the separate not-converging condition.
- On hardware, freeze the leader target and compare predictions with measured
  time to enter tolerance under representative poses and loads. Agree on an
  accuracy envelope and supported operating conditions before enabling advice.
- The one-second threshold refers to predicted catch-up duration, not elapsed
  time above a position-error threshold.
- Warnings and estimator work do not block the control loop; compare loop
  timing and audio latency against the existing 30 Hz baseline.
- Operator trials verify that warnings are understandable and not repetitive;
  warnings remain visible when speech is disabled.

Feature F5: Pickup mode after follower/leader divergence
-------------------------------------------------------
Priority: After the threshold measurement experiment; not implemented.

- Reuse the pickup concept referenced by the G1 VR lab history: suspend following,
  guide operator alignment, then resume without a target jump.
- G1 reference: sessions/2026-10-15-g1-vr-camera/session.md in the labbook,
  code reference 4d9d9724 (work/g1-vr-physical). That record reports virtual
  jump-free transitions; physical hold/recovery was not validated there.
- For SO101, distinguish normal lag from persistent error with little progress.
  An obstruction is one possible cause, not something position error alone proves.
- Determine and validate how to hold/support the follower without continuing to
  push into an obstacle; do not blindly latch an unreachable old leader target.
- While in pickup mode, ignore leader movement as a follower target and prompt
  the operator to align the leader to the measured follower pose.
- Require all relevant joints to be within configured tolerances for a dwell
  interval and explicit operator resume. Use fresh feedback and handle stale data.
- Distinguish pickup from torque-off, fault, physical obstruction clearance and
  emergency stop. Never automatically reverse or force through an obstruction.
- Define recording boundaries: pickup motion must not silently contaminate a
  demonstration; mark, pause or discard the interrupted episode explicitly.
- Validate first with mocks/simulation, then supervised clear-space physical
  alignment; do not deliberately block/stall the follower for a test.

    Implement F3 only after the basic workflow and timing are validated.

    then validate predictions and spoken warnings with an operator. This work
    does not depend on completing optional M5 or M6.
