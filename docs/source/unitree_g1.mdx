The Unitree G1 humanoid is now supported in LeRobot! You can teleoperate, train locomanipulation policies, test in sim, and more. Both 29 and 23 DoF variants are supported.

## Part 1: Getting Started

### Install the Unitree SDK

Follow the [unitree_sdk2_python installation guide](https://github.com/unitreerobotics/unitree_sdk2_python#installation). Tested with `unitree_sdk2py==1.0.1` and `cyclonedds==0.10.2`:

```bash
conda create -y -n lerobot python=3.12
conda activate lerobot
git clone https://github.com/unitreerobotics/unitree_sdk2_python.git
cd unitree_sdk2_python
pip install -e .
cd ..
```

### Install LeRobot

```bash
conda install ffmpeg -c conda-forge
conda install -c conda-forge "pinocchio>=3.0.0,<4.0.0"
git clone https://github.com/huggingface/lerobot.git
cd lerobot
pip install -e '.[unitree_g1]'
```

<Tip>
  For now, pinocchio must be installed from conda-forge (not pip) to include the
  CasADi bindings needed for arm IK.
</Tip>

### Test the Installation (Simulation)

The simulation environment has its own dependencies. Check the Simulation environment dependencies: [Unitree G1 Mujoco EnvHub](https://huggingface.co/lerobot/unitree-g1-mujoco/tree/main).

```bash
pip install mujoco loguru msgpack msgpack-numpy
```

```bash
lerobot-teleoperate \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --teleop.type=unitree_g1 \
  --teleop.id=wbc_unitree \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "localhost", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30, "warmup_s": 5}}' \
  --display_data=true \
  --robot.controller=GrootLocomotionController
```

This will launch a [MuJoCo sim instance](https://huggingface.co/lerobot/unitree-g1-mujoco/tree/main) for the G1. You can connect a gamepad to your machine before launching in order to control the robot's locomotion in sim. We support both [HolosomaLocomotionController](https://github.com/amazon-far/holosoma) and [GrootLocomotionController](https://github.com/NVlabs/GR00T-WholeBodyControl) via `--robot.controller`.

- Press `9` to release the robot
- Press `7` / `8` to increase / decrease waist height

#### Simulation with VR (IsaacTeleops)

Use an Isaac Teleop headset and controllers to move the simulated G1-29 arms
and base while viewing the simulated head camera in VR. Install the CloudXR and
video dependencies from the [Isaac Teleop guide](isaac_teleop) in the same Python
environment as LeRobot. Run the commands below from the LeRobot repository root.

On G1 onboard PC2, first load the environment provided by the
[`unitree_g1_dev` Isaac Teleop setup](https://github.com/MoissanClub/unitree_g1_dev/tree/main/pc2/IsaacTeleop).
This supplies the Jetson native libraries and EGL preload:

```bash
python_bin="$HOME/miniforge3/envs/lerobot-dev/bin/python"
lerobot_dir="$HOME/lerobot"
source "$HOME/unitree_g1_dev/pc2/IsaacTeleop/lerobot_env.sh"
lerobot_environment
cd "$lerobot_dir"
```

The pinned model downloads automatically on first use. Create a fresh directory
for the camera channel:

```bash
vr_run=$(mktemp -d /tmp/g1-vr-XXXXXXXX)
```

Review NVIDIA's CloudXR EULA before supplying the acceptance flag, then start:

```bash
MUJOCO_GL=egl lerobot-teleoperate \
  --robot.type=unitree_g1_motion \
  --robot.mode=simulation \
  --teleop.type=xr_controllers \
  --teleop.full_input=true \
  --teleop.terminal_control=true \
  --teleop.cloudxr_config=examples/unitree_g1/cloudxr_quest3.env \
  --teleop.accept_cloudxr_eula=true \
  --teleop.video_channel="$vr_run/camera.rgb" \
  --robot.video_channel="$vr_run/camera.rgb" \
  --teleop.video_openxr_composition=false
```

This launches G1-29 MuJoCo/GR00T with VR arm control and headset video, without
physical motor commands. The composition option avoids a black camera panel on Orin.

Keep the terminal running and put the headset on the same reachable network:

1. Open `https://<SIMULATION-HOST-IP>:48322` in the headset browser and accept
   the local certificate. Use the host's Wi-Fi/LAN address, not `localhost`.
2. Open the [NVIDIA Isaac Teleop client](https://nvidia.github.io/IsaacTeleop/client).
   The PC2 installer adds a certificate-page button that opens this client with
   the IP and port filled in. Otherwise, enter the host IP and port `48322`.
3. Select **H.264** on Orin, click **Connect**, then **Play** to enter VR.
   You should see the simulated robot camera view.

- Type `r` then Enter in the launching terminal to start arm/base tracking.
- Move each controller to move the corresponding arm; keep sticks centered to
  test arms first. Left stick controls translation; right stick controls yaw.
- Type `p` then Enter to pause, and `q` then Enter to quit.
- After tracking loss, wake both controllers and type `r` then Enter to resume.

This workflow uses a fixed G1-29 model with locked fingers; the end-effector
options below apply to `unitree_g1`. Add `--robot.onscreen=true` for an optional
desktop window with working OpenGL. Run one CloudXR/XR session at a time.

#### Choosing the End Effector

`--robot.end_effector` says what the arms carry: `dex1` for the parallel grippers (the default), `dex3` for the three-finger hands, or `dummy` for bare wrists. In simulation it picks the MuJoCo model, which decides the finger actuators and which cameras the scene carries — the wrist cameras are mounted on the end effector, so `dummy` only has `head_camera`.

```bash
lerobot-teleoperate \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --robot.end_effector=dex3 \
  --teleop.id=wbc_unitree \
  --robot.controller=GrootLocomotionController
```

The sim publishes the model's cameras over ZMQ on `--robot.sim_camera_port` (5555 by default), which is where the `zmq` cameras in `--robot.cameras` read them from. Pass `--robot.sim_publish_images=false` to open MuJoCo's interactive window instead: the sim renders either its cameras or its window, never both, since the offscreen contexts belong to the thread that creates them rather than to the viewer's. `--robot.sim_onscreen` names that choice outright rather than leaving it to the cameras, and asking for both is refused; set it and `--robot.sim_publish_images` both false to render neither, which is what a machine with no display can do.

### Connect to the Physical Robot

The G1's Ethernet IP is fixed at `192.168.123.164`. Your machine must have a static IP on the same subnet: `192.168.123.x` where `x ≠ 164`.

```bash
# Replace 'enp131s0' with your ethernet interface name (check with `ip a`)
sudo ip addr flush dev enp131s0
sudo ip addr add 192.168.123.200/24 dev enp131s0
sudo ip link set enp131s0 up
```

### SSH into the Robot

```bash
ssh unitree@192.168.123.164
# Password: 123
```

### Share Internet via Ethernet

The G1 needs internet access to clone repos and install packages. Share your laptop's connection over Ethernet:

**On your laptop:**

```bash
sudo sysctl -w net.ipv4.ip_forward=1

# Replace wlp132s0f0 with your WiFi interface name
sudo iptables -t nat -A POSTROUTING -o wlp132s0f0 -s 192.168.123.0/24 -j MASQUERADE
sudo iptables -A FORWARD -i wlp132s0f0 -o enp131s0 -m state --state RELATED,ESTABLISHED -j ACCEPT
sudo iptables -A FORWARD -i enp131s0 -o wlp132s0f0 -j ACCEPT
```

**On the G1:**

```bash
sudo ip route del default 2>/dev/null || true
sudo ip route add default via 192.168.123.200 dev eth0
echo "nameserver 8.8.8.8" | sudo tee /etc/resolv.conf

# Verify
ping -c 3 8.8.8.8
```

### (Optional) Enable WiFi on the Robot

For wireless SSH access, you can enable WiFi on the G1 (it's blocked by default):

```bash
sudo rfkill unblock all
sudo ip link set wlan0 up
sudo nmcli radio wifi on
sudo nmcli device set wlan0 managed yes
sudo systemctl restart NetworkManager
```

**Connect to a WiFi network:**

```bash
nmcli device wifi list

sudo nmcli connection add type wifi ifname wlan0 con-name "YourNetwork" ssid "YourNetwork"
sudo nmcli connection modify "YourNetwork" wifi-sec.key-mgmt wpa-psk
sudo nmcli connection modify "YourNetwork" wifi-sec.psk "YourPassword"
sudo nmcli connection modify "YourNetwork" connection.autoconnect yes
sudo nmcli connection up "YourNetwork"

ip a show wlan0
```

You can then SSH over WiFi instead of Ethernet:

```bash
ssh unitree@<ROBOT_WIFI_IP>
# Password: 123
```

## Part 2: Teleoperation & Locomotion

### Run the Robot Server

On the robot (from `~/lerobot`):

```bash
cd ~/lerobot
python src/lerobot/robots/unitree_g1/run_g1_server.py --camera
```

### Run the Locomotion Policy

You can run the teleoperation client from your laptop over Ethernet, over WiFi (experimental), or directly on the robot itself. Mind potential latency introduced by your network.

**From your laptop:**

```bash
lerobot-teleoperate \
  --robot.type=unitree_g1 \
  --robot.is_simulation=false \
  --robot.robot_ip=<ROBOT_IP> \
  --teleop.type=unitree_g1 \
  --teleop.id=wbc_unitree \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "<ROBOT_IP>", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --display_data=true \
  --robot.controller=HolosomaLocomotionController
```

We support both [GrootLocomotionController](https://github.com/NVlabs/GR00T-WholeBodyControl) and [HolosomaLocomotionController](https://github.com/amazon-far/holosoma) via `--robot.controller`.

### Physical VR Arm Teleoperation (Isaac Teleop)

Run on PC2 with the environment from
[Simulation with VR](#simulation-with-vr-isaacteleops). This workflow uses
`unitree_g1_motion`: arm targets go through `rt/arm_sdk` while the stock Unitree
controller retains balance. Stop the whole-body server from the preceding section
and other motion applications before using it. Do not release the stock motion mode.

#### View the Robot Camera

Discover the RGB device with `lerobot-find-cameras opencv` (or `realsense`) and
inspect its preview image. Replace index `4` below with the selected device:

```bash
camera_run=$(mktemp -d /tmp/g1-camera-XXXXXXXX)
lerobot-teleoperate \
  --robot.type=unitree_g1_motion \
  --robot.mode=camera \
  --robot.cameras='{"head": {"type": "opencv", "index_or_path": 4, "width": 640, "height": 480, "fps": 30}}' \
  --robot.video_channel="$camera_run/camera.rgb" \
  --teleop.type=xr_controllers \
  --teleop.terminal_control=true \
  --teleop.video_channel="$camera_run/camera.rgb" \
  --teleop.video_source=g1-29-physical-camera \
  --teleop.video_openxr_composition=false \
  --teleop.cloudxr_config=examples/unitree_g1/cloudxr_quest3.env \
  --teleop.accept_cloudxr_eula=true \
  --fps=30
```

Connect and Play as in simulation; video appears without `r`. This mode opens
only the camera, with no joint feedback or motion transport. Check the real
scene, orientation, color, and responsiveness. Camera timeouts replace stale
video with an unavailable placeholder. Type `q` then Enter to close the session
before starting arm control. The composition option is for Orin.

#### Check Feedback and VR Targets

Configure the Robot and Teleoperator directly. The Robot resolves its pinned model,
and LeRobot selects the VR action processor automatically. No generated configuration
or contract file is needed. Replace `enP8p1s0` with the robot-facing interface:

```bash
lerobot-teleoperate \
  --robot.type=unitree_g1_motion \
  --robot.mode=shadow \
  --robot.arm_sdk.network_interface=enP8p1s0 \
  --teleop.type=xr_controllers \
  --teleop.full_input=true \
  --teleop.terminal_control=true \
  --teleop.cloudxr_config=examples/unitree_g1/cloudxr_quest3.env \
  --teleop.accept_cloudxr_eula=true
```

Shadow mode reads joint feedback but never acquires arm authority. The terminal
prints the hardware mode and a fresh report path. Type `r` then Enter to inspect
proposed targets; check joint identity, starting posture, and left/right mapping.
`motor_publication` and `base_rpc` must remain false. Exit with `q` before continuing.
A reported mode byte must be checked against the manufacturer's operating procedure.

#### Run Physical Arm Teleoperation

Use the observed, approved mode as `G1_MODE_MACHINE`. Set `ARM_KP`, `ARM_KD`, and
`ARM_TORQUE_LIMITS` to reviewed JSON lists of 14 positive values, ordered left arm
then right arm: shoulder pitch/roll/yaw, elbow, wrist roll/pitch/yaw. The command
requires these explicitly; it does not choose physical gains or torque limits.

```bash
lerobot-teleoperate \
  --robot.type=unitree_g1_motion \
  --robot.mode=arms \
  --robot.enable_motion=true \
  --robot.enable_locomotion=false \
  --robot.arm_sdk.network_interface=enP8p1s0 \
  --robot.arm_sdk.expected_mode_machine="$G1_MODE_MACHINE" \
  --robot.arm_sdk.kp="$ARM_KP" \
  --robot.arm_sdk.kd="$ARM_KD" \
  --robot.arm_sdk.torque_limits="$ARM_TORQUE_LIMITS" \
  --teleop.type=xr_controllers \
  --teleop.full_input=true \
  --teleop.terminal_control=true \
  --teleop.cloudxr_config=examples/unitree_g1/cloudxr_quest3.env \
  --teleop.accept_cloudxr_eula=true
```

Joint bounds default to the selected model; `--robot.arm_sdk.lower` and `upper`
can narrow them. Velocity, acceleration, displacement, tracking-error, tilt, and
freshness limits remain enforced. The default per-session displacement is 0.05 rad.
Review payload/gravity, command ownership, stop behavior, and authority handover
before motion; retain an independent stop mechanism for process or network failure.

- `r` then Enter enables following; start still, then move one arm slightly.
- `p` pauses following without releasing torque. `q` exits and attempts handover.
- Tracking loss pauses following and requires `r` to resume. Restart after a
  transport/watchdog fault.

Mapping is continuous and head-relative, not squeeze-to-clutch. Sticks do not
command locomotion in arm mode; hands are not actuated. No collision avoidance
is provided. `--robot.assets` overrides the model location, and
`--robot.report_path` overrides the automatically created session report.
Existing `--robot.contract` files and saved action processors remain supported;
do not combine a contract with direct `--robot.arm_sdk.*` settings.

To include video during shadow or arm control, run the separate
`examples/unitree_g1/validate_xr_readonly.py camera` producer in another terminal
(see its `--help`). Add these options to the command above, using its channel path:

```bash
--teleop.video_channel=/tmp/lerobot-physical-camera.rgb \
--teleop.video_source=g1-29-physical-camera \
--teleop.video_openxr_composition=false
```

Only one process may own the camera. Stop camera-only mode first; do not pass
`robot.cameras` or `robot.video_channel` in shadow/arms mode.

## Part 3: Loco-Manipulation with the Homunculus Exoskeleton

We provide a loco-manipulation solution via the Homunculus Exoskeleton — an open-source 7 DoF exoskeleton for whole-body control. Check it out [here](https://github.com/nepyope/hmc_exo).

### Calibrate

```bash
lerobot-calibrate \
  --teleop.type=unitree_g1 \
  --teleop.left_arm_config.port=/dev/ttyACM1 \
  --teleop.right_arm_config.port=/dev/ttyACM0 \
  --teleop.id=exo
```

During calibration move each joint through its entire range. After fitting, move the joint in a neutral position and press `n` to advance.

### Record a Dataset

```bash
lerobot-record \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "localhost", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --teleop.type=unitree_g1 \
  --teleop.left_arm_config.port=/dev/ttyACM1 \
  --teleop.right_arm_config.port=/dev/ttyACM0 \
  --teleop.id=exo \
  --dataset.repo_id=your-username/dataset-name \
  --dataset.single_task="Test" \
  --dataset.num_episodes=2 \
  --dataset.episode_time_s=5 \
  --dataset.reset_time_s=5 \
  --dataset.push_to_hub=true \
  --dataset.streaming_encoding=true \
  --dataset.encoder_threads=2
```

> **Note:** Omit `--teleop.left_arm_config.port` and `--teleop.right_arm_config.port` if you're only using the joystick.

Example dataset: [nepyope/unitree_box_move_blue_full](https://huggingface.co/datasets/nepyope/unitree_box_move_blue_full)

## Part 4: Training & Inference

### Train

```bash
python src/lerobot/scripts/lerobot_train.py \
  --dataset.repo_id=your-username/dataset-name  \
  --policy.type=pi05 \
  --output_dir=./outputs/pi05_training \
  --job_name=pi05_training \
  --policy.repo_id=your-username/your-repo-id \
  --policy.pretrained_path=lerobot/pi05_base \
  --policy.compile_model=true \
  --policy.gradient_checkpointing=true \
  --wandb.enable=true \
  --policy.dtype=bfloat16 \
  --policy.freeze_vision_encoder=false \
  --policy.train_expert_only=false \
  --steps=3000 \
  --policy.device=cuda \
  --batch_size=32
```

### Inference with RTC

Once trained, we recommend deploying policies using inference-time RTC:

```bash
lerobot-rollout \
  --strategy.type=base \
  --policy.path=your-username/your-repo-id \
  --policy.device=cuda \
  --robot.type=unitree_g1 \
  --robot.is_simulation=false \
  --robot.controller=HolosomaLocomotionController \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "<ROBOT_IP>", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --task="task_description" \
  --duration=1000 \
  --fps=30 \
  --inference.type=rtc
```

## Part 5: SONIC Whole-Body Control (Latent-Token Policies)

LeRobot now ports the **decoder** half of NVIDIA's [SONIC](https://nvlabs.github.io/GEAR-SONIC/) whole-body deploy stack as the `SonicWholeBodyController`. Instead of commanding joints, the policy outputs a 64-D **latent motion token** (`motion_token.{i}.pos`) each tick; the SONIC decoder maps that token plus recent proprioception history onto a residual action that is scaled and added to the standing pose, producing 50 Hz joint-position targets for all 29 DoF.

The controller loads its ONNX decoder and all deploy constants (PD gains, `default_angles`, `action_scale`, and the neutral token) from [`lerobot/sonic_decoder`](https://huggingface.co/lerobot/sonic_decoder). The repo also ships a distilled low-latency decoder, selectable with the controller's `policy_type="low_latency"` argument (defaults to `"default"`).

### Test in Simulation

Any token-output policy trained on SONIC motion tokens (e.g. [`nepyope/sonic_walk`](https://huggingface.co/nepyope/sonic_walk)) can drive it:

```bash
lerobot-rollout \
  --strategy.type=base \
  --policy.path=nepyope/sonic_walk \
  --policy.device=cuda \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --robot.controller=SonicWholeBodyController \
  --robot.cameras='{"ego_view": {"type": "zmq", "server_address": "localhost", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30, "warmup_s": 15}}'
```

### Run on the Physical Robot

On hardware, run the policy with [async inference](./async) rather than a single `lerobot-rollout` loop. A rollout driven from your laptop puts the network in the middle of the control loop: every step blocks on inference, and one hiccup stalls the 50 Hz balance loop while the robot is standing on it. Async inference splits the two — the policy runs on your GPU machine, while the robot client runs on the G1's Jetson, so the SONIC controller thread and `rt/lowcmd` stay onboard and only 64-D token chunks cross the network.

Three processes, with the robot server from Part 2 running the whole time:

```text
GPU machine                     G1 (Jetson)
policy_server  ◄── gRPC ──►  robot_client: UnitreeG1 + SONIC decoder @ 50 Hz
  checkpoint                        │ ZMQ (lowcmd 6000, lowstate 6001, camera 5555)
                                    ▼
                             run_g1_server.py  ◄──► rt/lowcmd, rt/lowstate (DDS)
```

Start the policy server on the GPU machine first:

```bash
python -m lerobot.async_inference.policy_server \
  --host=0.0.0.0 \
  --port=8080 \
  --fps=30
```

On the robot, start the server (bridge + camera):

```bash
python src/lerobot/robots/unitree_g1/run_g1_server.py --camera
```

Then, in a second terminal on the robot, start the client. Everything robot-side is loopback, since the bridge runs on the same machine:

```bash
python -m lerobot.async_inference.robot_client \
  --server_address=<GPU_MACHINE_IP>:8080 \
  --policy_type=pi05 \
  --pretrained_name_or_path=nepyope/sonic_walk \
  --policy_device=cuda \
  --actions_per_chunk=50 \
  --fps=30 \
  --task="walk forward" \
  --robot.type=unitree_g1 \
  --robot.is_simulation=false \
  --robot.robot_ip=127.0.0.1 \
  --robot.controller=SonicWholeBodyController \
  --robot.cameras='{"ego_view": {"type": "zmq", "server_address": "127.0.0.1", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30, "warmup_s": 5}}'
```

A few things to keep in mind:

- `--policy_device` is the device the _server_ loads the policy onto — the client sends it during the handshake.
- `--actions_per_chunk` must not exceed the checkpoint's chunk size (50 for `nepyope/sonic_walk`).
- With `SonicWholeBodyController` the observation state is the 64-D token echo instead of the 29 joint positions, so the checkpoint has to be trained against that same state.

On connect, the robot eases every joint to the decoder's `default_angles` before the controller takes over, so the first policy commands don't snap from the connect-time pose.
